# Local quota reset reminders

Mac and iPhone have independent opt-in switches, off by default. The default advance notice is 15 minutes; choices are 5, 15, 30 and 60. Both surfaces use the existing system notification permission. Enabling local reminders never enables sync, registers an APNs token, or changes Cloudflare alerts. No new entitlement, credential, remote service or deployment is needed.

## Forecast policy

`ResetReminderPolicy` only creates future reminders from reported, available quota windows with a successful fetch, a fresh per-window observation, a known future reset, and a trusted clock offset (within 120 seconds). Manual reset-credit cards and cumulative spending metrics are excluded. A reminder whose advance-notice time has passed is skipped, without catch-up delivery.

The request ID hashes the source device and epoch, provider/account/window identity, canonical UTC reset instant and chosen lead time. Snapshot sequence, channel and user alias do not change that identity. A cycle hash omits the lead time: changing the setting replaces a pending timing but does not repeat an already handled cycle. Replacement evidence carries the old fire deadline and is rechecked after authorization and before each add, so a pending query captured before a suspension cannot authorize a replacement after that deadline. Triggers use a Gregorian UTC calendar, so DST and device timezone changes do not move the reset instant.

At most 48 owned requests are scheduled, with a conservative total budget of 64 pending requests after reserving space for other notification features. The coordinator retains at most 48 request records and 2048 active cycle markers. Markers expire after their reset; an active-history capacity limit stops new scheduling and reports capacity without dropping existing suppression. Per-window observation high-water hashes survive restart (up to 2048, pruning inactive entries after 30 days) so a newer snapshot sequence cannot schedule an older observation. Other notification features are unaffected because cleanup and foreground presentation only match `ammo-reset-v1-`.

## Lifecycle and persistence

Accepted forecasts remain queued when the phone refresh fails or the Mac provider returns retained stale/error observations. Cached data alone never creates a new reminder. A verified snapshot removes forecasts for missing windows or explicit unavailable/auth-required/disabled windows. Pausing/removing Mac accounts, disabling all phone sources, CloudKit account loss, revoked pairing and credential replacement cancel the affected source's forecasts. A cryptographically accepted different source epoch invalidates the previous epoch even when its observations are retained offline or clock skew prevents new scheduling. Lower same-epoch snapshot sequences are rejected before changing the latest input.

The local Application Support ledger uses `QuotaStore.PrivateFile` atomic private-file writes. It contains settings, hashed identities and forecast timestamps; no snapshot plaintext, aliases, notification bodies or credentials. Prepared records and conservative cycle markers are persisted before asking the OS to add a request, then committed after acceptance. Restart reconciles them with pending OS IDs. Unresolved preparation remains suppressed until reset, including when its fire time elapsed while the app was closed: absence from pending never proves that it did not fire. Older prepared ledgers without a marker receive the same protection before records are discarded. Confirmed future cancellation can release suppression; an explicit add rejection or a request skipped before calling the OS also releases its preparation marker. A future cycle can re-arm after cancellation only when a pre-removal query reports its request present and a subsequent post-removal query reports it absent while the current clock is still before its original fire deadline. Invoking the asynchronous OS removal API alone is not proof. Delayed, missing or inconclusive evidence keeps suppression until reset, including across source changes and restart. A lead-time change therefore may leave this cycle suppressed and take effect for later cycles instead. Corrupt/unwritable ledgers fail closed. Every failed persistence exit invalidates scheduling and authorization generations and requests removal of all known active/prepared/cancelled and last-observed owned IDs, even when the failing write cancelled only a subset; cycle evidence is retained and unrelated notifications are untouched. OS removal remains asynchronous.

Authorization, pending queries and notification adds may suspend. An injected clock advances scheduling eligibility after waits and before each add, including backward clock changes. A persisted evaluation-time high-water mark blocks new scheduling more than 120 seconds behind previously evaluated device time, preventing an expired cycle pruned after a forward jump from becoming eligible after a rewind. Authoritative cancellations still run first. An erroneous forward clock can therefore suppress new reminders until the clock catches up; refreshing alone does not clear that conservative limit. The settings UI explains both clock uncertainty and suppressed cycles. Authoritative window revocations cancel even when clock skew prohibits new forecasts. Preference/account/source generations invalidate late completions. Disable and source invalidation immediately request removal of every known/prepared ID; OS removal has no completion callback. Persisted cancellation records survive until a post-removal query confirms their IDs absent. IDs still reported pending remain durable, are retried on restart and reconciliation, are included in credential-transition cleanup markers, and count toward the 48-record bound. Queued cancellation waits for prior adds before its post-removal pending query, and direct account/window/offset replacements use the same before/after proof with the current clock. A post-removal absence returned after the old fire time cannot distinguish cancellation from delivery and never releases suppression. Apple callback ordering is not assumed, and tests include deferred removal and delayed responses rather than treating removal invocation as completion. Cleanup barriers remain ahead of replacements, and a stale add completion requests removal of its own ID. The ledger also records reminder transport provenance, so a restored CF forecast is cancelled on 401/403 even with no displayed snapshot. Revocation and transport-disable handlers check both that persisted forecast owner and the latest cached or queued snapshot owner. This invalidates cached iCloud eligibility while reminders are off and prevents an in-flight CF-to-iCloud update from scheduling after a CloudKit account change, even when both transports remain enabled. Accepted account-unavailable/account-mismatch errors also invalidate that eligibility synchronously in the iCloud catch, before awaiting Cloudflare networking; stale refresh identities cannot apply the revocation. Before pairing or rotation writes replacement viewer credentials, the phone durably records a bounded marker of hashed owned request IDs and invalidates reminder source state; any failed preparation write aborts the credential commit. Restart immediately requests marked cleanup, including after a crash between ledger and credential writes. New scheduling waits for a post-removal query to report those IDs absent before retiring the marker; this does not claim that past delivery was prevented. Credential transitions swap clients/scopes before suspension, exclude refresh while transitioning, and accept results only for the captured generation, scope and client identity; owner tokens prevent an old transition from unlocking a newer one. Mac startup first reads and validates local connection intent without migration writes, secret cleanup or networking, and cancels paused/removed account forecasts before bootstrap, projection, MCP or Worker recovery awaits. Missing or unreadable configuration cannot establish any enabled account and conservatively cancels known forecasts. Every successful validated configuration write applies allowed account intent synchronously before activation can suspend, including replacement, pause, removal, cleanup and durable rollback. Display summaries and an unpersisted runtime fallback cannot restore excluded account eligibility. A failed configuration write can leave the rename completed before directory durability is acknowledged, so that failure treats account intent as unknown and cancels known forecasts until a successful write or validated startup read establishes intent. At startup, the phone synchronously loads persisted transport preferences (including the existing paired-installation migration) and reconciles restored ownership before its first ActivityKit or network suspension. A disabled owner is invalidated without waiting for another transport or a replacement snapshot. The phone calls the same reconciliation from its existing foreground/background refresh path; it creates no new background cadence.

## Runtime limits and verification

Once queued, the OS can deliver a local reminder while the app is suspended or closed. The app cannot verify quota freshness at delivery, discover a changed reset without another refresh, or guarantee a banner at the requested instant. Permission, Focus, system notification settings and sleep can affect presentation. No continuing background polling or reset confirmation is promised; notification copy explicitly says the reset is expected and asks the user to refresh.

Mac and phone foreground delegates present banners/sound/list for this feature's prefix only. Other foreground notification behavior is unchanged.

`tests/ios/ResetReminderTests.swift` uses synthetic snapshots, fake permission/notification clients and isolated memory storage. It covers UTC/DST equivalence, multi-account identity, freshness/skew/reset-credit exclusions, offset/reset replacement, offline preservation and cancellation, cap/account filtering, restart and interrupted acceptance, permission/add races, epoch replacement, and ledger failures/privacy. Fixtures, unbundled SwiftPM processes and XCTest (including a native app host) use volatile storage and disable the system notification adapter, so tests cannot modify a user’s ledger or pending notifications. Unit tests do not demonstrate physical iPhone notification acceptance or delivery; native builds and device verification remain separate checks.

Mac reminder persistence uses the existing owner-only QuotaIsland data directory. The historical Ammo UI directory can have broader permissions; its permissions and contents are left untouched. Native notification delivery and physical phone acceptance remain unverified.
